JobPilot: where to draw the line between a 1.7B model and a big one

A job application pipeline built for a 2019 Intel MacBook with no GPU. Every task goes to the smallest model that can do it, and the split is drawn on one rule: if the output reaches a recruiter, a large model writes it.

Role
Solo. Pipeline, model routing, LaTeX tailoring, browser automation.
Stack
Python, Ollama (Qwen3 1.7B), Claude API, Playwright, LaTeX
Hardware
Intel i5, 16 GB, no GPU, no PyTorch build, no compile step

The constraint that shaped it

The machine is a 2019 Intel MacBook Pro: quad-core i5, 16 GB, no GPU. That rules out running anything substantial locally in the usual sense — no PyTorch, no llama.cpp build, no compile step. What it does not rule out is a small model served over HTTP by Ollama, which turns out to be enough for a surprising share of the pipeline. The local model takes 5 to 15 seconds per task on CPU and the fan stays quiet.

So the design question is not "can I run a model" but "which tasks am I willing to hand to a 1.7B one". The rule I settled on is a single line, and it is about consequences rather than difficulty.

TaskRuns onWhy
Extracting structured fields from a postingQwen3 1.7BShort, mechanical, JSON-shaped
Quick apply/skip pre-screenQwen3 1.7BOne sentence, throwaway
Detecting the ATS platformQwen3 1.7BClassification over page signals
Mapping form fields to profile dataQwen3 1.7BClassification, about 10 seconds
Full fit analysisClaude SonnetJudgement you actually read
Rewriting the LaTeX CVClaude SonnetAffects hiring decisions
Writing the cover letterClaude SonnetAffects hiring decisions
Answering screening questionsClaude SonnetGoes in front of a recruiter

If Ollama is down or the local model starts misbehaving, JobPilot prints one warning and routes every task to the large model for the rest of the run. It never silently stalls, and it never silently degrades — those are the two ways a hybrid pipeline goes wrong without telling you.

The pipeline

Tailoring a CV without letting it drift

The canonical CV is a multi-file LaTeX project. The tree is copied into the application folder and only four section files are rewritten — profile, experience, projects, skills. The model reorders bullets so the most relevant lead, works the posting's vocabulary in where it honestly applies, and rewrites the sidebar profile for the role. It does not invent anything.

The interesting bit is what happens on a second pass. After a diff you can type tweak with an instruction — "lead with the thesis", "say SQL not databases" — and the model revises. That revision is validated against the base CV rather than the previous revision, so repeated tweaks cannot walk past the structural limits one small step at a time. Nothing compiles until you approve it.

The cover letter is handled the other way round. It is a personalisation of an existing letter, not a fresh draft: the story paragraphs are its spine, so they are substituted verbatim in code and the model only fills placeholders and rewrites the one bridge paragraph. A model rewriting the whole letter each time produces something fluent and slightly different from what I would say, which is exactly the failure I wanted to make structurally impossible.

Filling forms, and stopping

The apply stage opens Chromium — visible, never headless — detects the applicant tracking system and warns up front when it is one of the awkward ones. It fills the identity fields, uploads the PDF and pastes the letter. Open-ended questions get a short generated answer that is pasted, highlighted yellow, and announced for review. Anything it is unsure of gets highlighted and handed back with a pause.

Three rules enforced in code rather than in a prompt: it never clicks Submit, never creates accounts, and never solves CAPTCHAs. It stops in front of the final button and waits. A prompt asking a model not to do something is a request; a branch that has no code path to the Submit button is a guarantee, and for anything that acts on a real site on someone else's behalf that difference is the whole design.

The health check

Five dependencies have to line up — an API key, Ollama with the model pulled, pdflatex, Playwright browsers, a writable output directory — and each fails differently. The startup check prints one line per dependency with the exact command to fix it, and distinguishes degraded-but-usable (○, you keep the .tex instead of a PDF) from will-not-run (✗). Setup failures are the most common way a tool like this gets abandoned, so they get the same care as the pipeline.
