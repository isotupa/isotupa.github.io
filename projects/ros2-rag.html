ROS2 RAG, and a harness that measures it

A question-answering system over the ROS2 documentation. The retrieval part is the easy half. The part I built this for is the half that tells you whether it works.

Role
Solo. Ingestion, retrieval, evaluation harness, dashboard.
Stack
Python, Chroma, Ollama, bge-small-en-v1.5, cross-encoder reranker, ragas, Streamlit, pytest
Runs on
A CPU-only laptop. No API keys, no hosted models.

The question worth asking

Building a RAG demo is a weekend. The interesting question isn't "can it answer" — it will always answer. It's did retrieval pull the right passage, and did the model stay inside it or fill in the gaps from memory. Those are two separate failure modes and a single end-to-end score hides both.

So most of the code here grades those two things across a fixed set of questions, and compares a naive configuration against a tuned one on the same corpus with the same model.

Embedder / generatoridentical in both — bge-small-en-v1.5 and llama3.2:3b

Holding the embedder fixed is deliberate: it means any movement between the two rows comes from chunking and reranking rather than from a better vector space. Comparing embedders is the obvious next experiment, and the code supports a full sweep over chunk size, overlap, top-k and reranker on/off — I ship the two ends that show the clearest difference.

How the harness works

A gold set that makes retrieval scoreable

For a sample of documents, the model writes one question and a reference answer, and I record which document it came from. That recorded document is the correct retrieval target, and it is what turns retrieval metrics into measurements rather than guesses. The set is stored as JSON and versioned, so two runs are compared on the same questions.

Retrieval metrics with no model in the loop

precision@k, recall@k, nDCG, MRR and hit@k, written by hand and unit tested. They grade per document: did a chunk from the right document appear in the top k, and how high. No model touches them, so these numbers are exact — which is why they carry more weight than anything else the harness reports.

Two judges, kept apart

One checks faithfulness: is the answer supported by the text that was actually retrieved. The other checks correctness against the reference answer. They have to be separate, because an answer can be correct and ungrounded — the model knew it from training rather than from your documents — and that is precisely the failure mode you want to be able to see. Each returns a 1–5 score and a line of reasoning through Ollama's JSON schema mode so the scores parse cleanly.

A cross-check and a clock

ragas runs its own faithfulness, answer-relevancy and context-precision metrics over the same outputs. If my hand-rolled numbers and ragas point the same way I trust them more; if they diverge there is a bug to find. Separately, every call is timed and its tokens counted, so p50/p95 latency and tokens per second sit next to the quality numbers. Reranking usually improves quality and always adds latency, and that trade is the whole reason the harness exists.

The judge is a 3B model on a laptop, and it also wrote the gold set. So the judge scores are directional, not ground truth. The retrieval metrics are exact because no model touches them, and the thing to read is the movement from baseline to tuned rather than the absolute value. Swapping in a stronger judge is one config value. I would rather say this plainly than publish a table that implies more than the setup can support — which is also why the results table in the repository ships empty, with instructions to generate the numbers rather than a screenshot to trust.

Running it

ollama pull llama3.2:3b

python -m ros2_rag.ingest --limit 300
python -m ros2_rag.index --config config/baseline.yaml
python -m ros2_rag.index --config config/tuned.yaml
python -m ros2_rag.eval.goldset --n 60 --seed 13
python -m ros2_rag.eval.run_eval --config config/tuned.yaml
python scripts/make_table.py            # results JSON → markdown table
streamlit run dashboard/app.py          # both configs, per-question drill-down

make all does that in order, and make eval-quick runs 10 questions instead of 60 so you can confirm the whole thing works before leaving the full run going. The Streamlit dashboard is the easiest way to read a run: the two configs side by side, and per question the retrieved chunks, the answer, and what each judge said about it.

Known gaps

  • The judge is small, and it wrote the gold set. A hand-curated set would be better.
  • Only two configurations ship, not a sweep.
  • The embedder is fixed across both, so it is not part of the comparison.

If I took this further, the next thing would be a grid of configurations plotting quality against latency — because that curve is the answer the harness was built to produce, and two points is not a curve.

A note on Intel Macs. torch stops at 2.2.2 on Intel macOS, which forces numpy<2 and older transformers and sentence-transformers. Those versions are pinned in pyproject.toml, so a clean install works instead of walking into the compatibility wall.
